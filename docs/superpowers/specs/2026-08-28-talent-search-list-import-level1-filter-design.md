# 인재검색 자동화 — 실제 후보 리스트 가져오기에 최소 자동 필터 + 자동 페이지 넘김 적용 설계

- 작성일: 2026-08-28
- 원본 명세: `인재검색_자동화_마스터프롬프트_원본.md` (5장 "1단계 활동성·경력안정성 필터(Level 1)", 특히 5.1 이력서 업데이트일 / 4장 "목록 단계 1차 선별 기준"의 SKIP_CLEAR_MISMATCH 개념)
- 관련 기존 문서: `docs/superpowers/specs/2026-08-27-talent-search-real-list-import-design.md`(이번에 확장하는 "실제 후보 리스트 가져오기" 기능 원설계)

## 배경

2026-08-27에 완료한 "실제 후보 리스트 가져오기"를 실사용해본 뒤, 사용자(윤혜민)가 "화면에 보이는 걸 그냥 그대로 복사해오는 것뿐이라 번거롭다"는 피드백을 줬다. 이 대화에서 다음을 확정했다.

- **가져온 뒤에 화면에서 걸러내는 게 아니라, 가져오는 시점(저장 전)에 명확히 조건 밖인 사람은 아예 저장하지 않는다.** ("애초에 가져오는것부터 1차 레벨을 통과해야 가져올 수 있게")
- 리스트 카드에 이미 나오는 정보만으로 판단 가능한 두 가지만 이번에 적용한다:
  1. **이력서 최종업데이트일** — 기존 Level1 정책(`level1Rules.resumeUpdated`)의 FAIL 기준(기본 180일 초과)을 그대로 재사용
  2. **경력연수** — 검색 프로젝트 생성 시 입력하는 "희망 경력 범위"(`experienceMinYears`/`experienceMaxYears`)를 명확히 벗어남
- **재직여부는 이번 범위에서 뺀다** — "재직 중인 사람만"류 조건 자체가 이 시스템에 없어서(프로젝트 입력 화면에도 그런 필드가 없음), 새 조건 필드를 만드는 건 별도 논의가 필요한 큰 범위라 이번엔 제외.
- **애매하면 걸러내지 않는다.** 원본 명세 4장의 원칙("확실하지 않은 사람은 성급히 탈락시키지 말고 상세 검토 대기에 넣는다")을 그대로 따른다 — 날짜/경력 텍스트를 못 읽으면 그냥 들여온다. 이건 이 프로젝트가 다른 곳(OCR 추출)에서 쓰는 "실패하면 에러로 드러낸다"는 fail-closed 원칙과는 다른 문제다 — 여기서 다루는 건 에러 처리가 아니라 "판단 불가 = 배제하지 않음"이라는 채용 실무상의 안전장치다.

필터를 붙이고 나니 자연스럽게 이어진 두 번째 논의: 필터를 통과하는 인원이 페이지(약 20명)당 그보다 적을 수 있으니, 목표 인원(예: 50명)을 채우려면 여러 페이지가 필요하다. 원래 "실제 후보 리스트 가져오기" 설계(2026-08-27)는 **한 페이지만** 가져오도록 의도적으로 제한했었다 — 사람인이 그날 실제로 2단계인증을 띄운 적이 있어서(자동화된 움직임에 대한 실제 탐지 신호), 여러 페이지를 자동으로 넘기는 건 위험할 수 있다는 판단이었다. 이번에 다시 논의해서 다음을 확정했다.

- **확장이 "다음 페이지" 버튼까지 대신 클릭해서 목표 인원을 채운다.** 사용자는 "가져오기" 한 번만 누른다.
- 단, 안전장치를 명시적으로 둔다: 최대 페이지 수 상한, 페이지 사이 지연, 로그인/인증 화면 감지 시 즉시 중단(기존 원칙 재사용) — 아래 "자동 페이지 넘김" 절 참고.

## 이번 슬라이스 범위

**포함**:
- `POST /api/talent-search-projects/:id/list-candidates`(기존 엔드포인트)가 저장 전에 각 후보를 판정해서, 명확히 조건 밖인 후보는 DB에 저장하지 않는다.
- 응답에 저장/제외 인원수와 제외 사유 요약을 추가.
- 크롬 확장이 목표 인원을 채울 때까지(또는 안전 상한에 도달할 때까지) "다음 페이지" 버튼을 자동으로 클릭하며 반복 수집.
- 판정 로직은 DB 의존성 없는 순수 함수로 분리해 단위테스트.

**제외 (다음 단계로 미룸, 필요시 재논의)**:
- 재직여부 필터
- 제외된 후보를 어딘가에 기록해서 나중에 "몇 명이 왜 제외됐는지" 다시 확인하는 기능(감사로그 등) — 지금은 가져오기 시점의 응답 메시지로만 확인 가능하고, 그 순간이 지나면 사라진다.
- 단기근속·경력공백 등 리스트에 안 나오는 Level1 항목(이전부터 범위 밖으로 명시돼 있던 것 그대로 유지)
- 이 필터 자체를 켜고 끄는 설정(이번엔 항상 켜짐)
- 여러 페이지에 걸쳐 같은 후보가 중복으로 나올 때 서버 쪽에서 영구적으로 걸러내는 것(DB 유니크 제약 등) — 아래 "자동 페이지 넘김"의 세션 내 중복 방지는 별개로 포함

## 판정 기준 상세

### 1. 이력서 최종업데이트일

- 리스트 카드의 `lastUpdatedLabel`은 `"26-06-10 업데이트"` 형식(사람인 실제 확인됨, `chrome-extension/list-content-lib.js` 기존 파싱 결과 그대로 재사용 — 파싱 로직 변경 없음).
- `YY-MM-DD`를 20YY년으로 해석해 오늘과의 일수 차이(`resumeAgeDays`)를 계산한다.
- 이 프로젝트가 검토 시점에 고정해 둔 채점 기준(`talent_search_projects.policy_version_id`)의 `level1Rules.resumeUpdated.verifyWithinDays`(기본값 180)를 초과하면 **제외**. 이 값 이하면(90일 이내 PASS든 91~180일 VERIFY든) 통과 — VERIFY 구간까지는 원본 명세도 "제외"가 아니라 "확인 필요"로 다루므로, 저장은 하되 구분 표시는 하지 않는다(범위 밖, 아래 "알려진 한계" 참고).
- `lastUpdatedLabel`이 없거나 형식이 안 맞으면(파싱 실패) 판단 불가로 보고 **통과**시킨다.
- 프로젝트가 아직 승인 전이라 `policy_version_id`가 비어 있는 경우(정상 흐름에서는 "검색 진행" 화면 자체가 승인된 프로젝트에만 있어 발생하지 않지만 방어적으로 다룸) 이 기준은 건너뛴다(통과) — 기준 버전이 없는데 억지로 지금 활성 정책을 가져다 쓰면, 나중에 정책이 바뀌었을 때 "그때 왜 걸렀는지"를 설명할 수 없어서다.

### 2. 경력연수

- 리스트 카드의 `careerSummary`는 `"경력 5년 3개월"` 또는 `"신입"` 형태(사람인 실제 확인된 유일한 예시가 "경력 5년 3개월"이라, 그 외 형식은 아래 "판단 불가" 규칙으로 안전하게 처리된다).
- `N년`과 `M개월`을 각각 정규식으로 뽑아 `연차 = N + M/12`로 환산한다. "신입"이면 0년. 둘 다 없으면 판단 불가.
- 프로젝트의 `experienceMinYears`/`experienceMaxYears`(둘 다 nullable) 범위를 **0.5년 여유를 두고** 벗어나면 제외한다(`연차 < 최소 - 0.5` 또는 `연차 > 최대 + 0.5`일 때만 제외) — 예: 최소 5년 요건에 4.6년 경력자는 통과하지만 4.4년 경력자는 제외된다. 반올림·근속 계산 오차로 흔히 생기는 경계값이라 무리하게 걸러내지 않기 위한 여유분이다. 이 여유값은 정책 편집 화면(기준 관리센터)의 대상이 아니라 코드 상수로만 관리한다(제품 정책이 아니라 "어느 정도까지 오차를 봐줄지"의 구현 디테일이라서).
  - 프로젝트가 최소/최대 경력을 아예 입력 안 했으면(둘 다 null) 이 기준 자체를 적용하지 않는다.
- `careerSummary`가 없거나 형식이 안 맞으면 판단 불가로 보고 **통과**.

### 판정 결과 종합

- 두 기준 중 하나라도 "명확히 벗어남"이면 그 후보는 저장하지 않는다(OR 조건 — 원본 명세의 "필수조건 불충족 또는 제외조건 일치가 명확하면 SKIP"과 같은 구조).
- 판단 불가는 항상 "통과"로 취급 — 하나만 판단 불가여도 다른 기준에서 명확히 걸리면 그 후보는 여전히 제외된다.

## 구현 위치

- 새 파일 `handlers/_lib/talentSearchListFilter.js`: `parseResumeAgeDays(label, refDate)`, `parseCareerYears(text)`, `evaluateListCandidate(candidate, { level1Rules, experienceMinYears, experienceMaxYears }, refDate)` 세 개의 순수 함수. `db.js`를 import하지 않아 `DATABASE_URL` 없이 `node --test`로 검증 가능(`handlers/_lib/talentSearchPolicyValidate.js`가 이미 쓰는 패턴과 동일한 이유 — 핸들러 파일 통째로 import하지 않고도 로직만 테스트).
- `handlers/talent-search-projects/[id]/list-candidates.js`(기존 파일) 수정:
  - 프로젝트 조회 쿼리에 `experience_min_years, experience_max_years, policy_version_id`를 추가로 select.
  - `policy_version_id`가 있으면 `talentSearchPolicy.js`에 새로 추가하는 `getPolicyById(id)`로 그 버전의 `level1_rules`를 가져온다.
  - `body.candidates`를 `evaluateListCandidate`로 나눠 저장할 것/제외할 것으로 분리, 저장할 것만 기존 INSERT 트랜잭션에 포함.
  - 응답을 `{ imported, skipped, skippedReasons: { resumeStale, careerOutOfRange } }`로 확장(기존 `{ imported }` 소비처인 `chrome-extension/popup.js`도 같이 수정).

## 자동 페이지 넘김

### 목표 인원

- 팝업에 "목표 인원" 숫자 입력칸을 추가한다. 기본값 50, 직접 수정 가능. 프로젝트의 `dailyRecommendCap`/`targetRecommendCount`와는 별개 개념이다 — 그 값들은 "채점 이후 하루에 추천할 인원"이고, 이건 "이번 가져오기 한 번에 리스트에서 몇 명이나 확보할지"라 성격이 다르다(하나를 다른 하나의 기본값으로 끌어쓰면 나중에 두 개념이 헷갈릴 수 있어 분리한다).
- "목표 인원"은 **필터를 통과해 실제로 저장된 인원 수** 기준이다 — 제외된 인원은 세지 않는다.

### 반복 흐름 (팝업이 주도)

기존에는 팝업이 "현재 페이지 파싱 → 서버 전송"을 한 번만 했다면, 이제 다음을 목표 인원에 도달하거나 중단 조건을 만날 때까지 반복한다.

1. 현재 탭에 `PARSE_CURRENT_LIST` 전송 → 후보 목록 파싱(기존 로직 그대로, 로그인/인증 화면이면 `blocked:true`로 즉시 중단).
2. 이번 페이지에서 새로 보는 후보만 서버로 전송 — 팝업이 세션 동안(이번 "가져오기" 클릭 한 번) 이미 본 `sourceUrl`을 `Set`으로 기억해서 중복 전송하지 않는다(페이지 넘김이 실제로는 안 먹혀서 같은 페이지를 다시 읽는 경우를 이 방식으로 자연스럽게 감지 — 새 후보가 0명이면 "더 이상 새 후보 없음"으로 보고 중단).
3. 서버 응답의 `imported`를 누적한다. 화면에 진행 상황을 실시간으로 보여준다(예: "2페이지째 · 지금까지 27명 확보").
4. 누적 `imported` ≥ 목표 인원이면 종료, 최종 요약 표시.
5. 지금까지 처리한 페이지 수가 안전 상한(**5페이지**)에 도달했으면 종료 — "안전 상한에 도달해 멈췄어요. 필요하면 사람인에서 직접 다음 페이지로 이동한 뒤 다시 눌러주세요." 안내. 상한은 코드 상수(한 번의 클릭이 무한정 페이지를 넘기지 않도록 하는 안전장치이지, 정책값이 아니다).
6. `CLICK_NEXT_PAGE`를 현재 탭에 전송 — 콘텐츠 스크립트가 "다음 페이지" 요소를 찾아 클릭한다. 요소를 못 찾으면(`hasNextPage:false`) 마지막 페이지로 보고 종료.
7. 사람처럼 보이도록 페이지 이동 후 **2.5~4.5초 사이 무작위 지연**을 두고 나서 1번으로 돌아간다(페이지가 완전히 다시 그려질 시간도 겸함).

### 안전장치

- **로그인/인증 화면 감지**: 매 반복의 1번 단계가 기존 `isBlockedPage` 검사를 그대로 거친다 — 페이지 넘김 중 사람인이 인증을 요구하면 다음 파싱 시도에서 바로 걸려 중단된다. 새로 만드는 `CLICK_NEXT_PAGE` 핸들러도 클릭 전에 같은 검사를 한 번 더 한다(클릭 자체가 예상 못한 팝업/리디렉션을 유발할 수 있어서 이중으로 확인).
- **페이지당 최대 5페이지**(위 5번) — 사람인 세션당 한 번의 "가져오기" 클릭이 만들 수 있는 요청 수를 명시적으로 제한한다.
- **페이지 이동 후 무작위 지연** — 매번 정확히 같은 간격으로 클릭하지 않도록 2.5~4.5초 범위에서 무작위 값을 고른다.
- **새 후보 0명이면 즉시 중단** — 다음 페이지가 실제로 안 넘어갔거나(선택자 문제, 사이트 변경) 마지막 페이지를 넘어간 경우를 자동으로 감지해 무한 루프를 막는다.
- 이 흐름 전체는 사용자가 "가져오기"를 누른 시점부터 시작해서 목표/상한/중단조건 중 하나에 닿으면 스스로 끝난다 — 사용자가 매 페이지마다 다시 클릭할 필요는 없지만(오늘 확정한 방향), 사람인 검색을 새로 실행하거나 검색어를 바꾸는 것은 여전히 사용자가 직접 한다(원 설계의 "확장은 검색을 대신하지 않는다" 원칙은 안 바뀜).

### 구현 위치

- `chrome-extension/list-content.js`: 새 메시지 타입 `CLICK_NEXT_PAGE` 핸들러 추가. "다음 페이지" 요소의 실제 선택자는 아직 모른다 — 카드 선택자(`.talent_list_item`)를 정했을 때와 같은 방식으로, 구현 시점에 실제 사람인 화면에 로그인해서 라이브 DOM을 직접 확인한 뒤 정한다(여기서 미리 추측해서 못박지 않는다). 요소를 찾으면 클릭 후 `{hasNextPage:true}`, 못 찾으면 `{hasNextPage:false}` 응답.
- `chrome-extension/popup.js`: 기존 `importBtn` 클릭 핸들러를 위 7단계 루프로 교체. 목표 인원 입력칸, 진행 상황 표시용 상태 텍스트 갱신 추가.

## 크롬 확장 변경사항

- `chrome-extension/popup.js`의 가져오기 결과 메시지가 페이지별 누적을 반영한다 — 예: `"2페이지에 걸쳐 52명 가져왔어요 (8명은 조건에 안 맞아 제외)"`. 목표 인원 전에 상한/마지막페이지로 멈췄으면 그 사유도 같이 보여준다.
- 리스트 카드 파싱 로직(`list-content-lib.js`)은 변경 없음 — 이미 필요한 원본 필드(`careerSummary`, `lastUpdatedLabel`)를 다 보내고 있다.

## 테스트

- `handlers/_lib/talentSearchListFilter.test.js`(신규): 날짜 파싱 경계값(정확히 180일, 179일, 181일, 형식 깨짐), 경력연수 파싱("경력 5년 3개월", "신입", 형식 깨짐), 종합 판정(둘 다 통과/하나만 걸림/둘 다 걸림/프로젝트가 min·max 둘 다 null인 경우) 커버.
- `development` 브랜치에서 실제 프로젝트로 curl 검증: 이력서 업데이트가 오래된 더미 후보와 경력 범위 밖 더미 후보를 섞어 보내고, 응답의 `imported`/`skipped`/`skippedReasons`와 실제 저장된 행이 일치하는지 확인.
- 실제 사람인 화면에서 반드시 끝까지 실사용 검증: (a) 목표 인원보다 한 페이지 인원이 적어 여러 페이지를 실제로 넘기는지, (b) 마지막 페이지에서 정상 종료하는지, (c) 안전 상한(5페이지)에서 정상 종료하는지, (d) 이 세션 중 우연히 로그인/인증 화면을 만나면 즉시 멈추는지. 크롬 확장은 서브에이전트가 검증할 수 없으므로(샌드박스, 브라우저 접근 불가) 컨트롤러가 사용자와 함께 직접 진행한다 — 2026-08-27 인수인계 문서에 이미 기록된 원칙과 동일.

## 알려진 한계 (의도적으로 이번 범위 밖)

- 제외된 후보는 어디에도 기록되지 않는다 — "가져오기" 버튼을 누른 그 순간의 응답 메시지로만 몇 명이 왜 제외됐는지 알 수 있고, 나중에 다시 확인할 방법이 없다.
- 재직여부 필터 없음(위 배경 절 참고).
- 이력서 업데이트일이 VERIFY 구간(91~180일)인 후보와 PASS 구간(90일 이내) 후보를 화면에서 구분 표시하지 않는다 — 둘 다 그냥 저장된다.
- 0.5년 경력 여유값은 코드 상수라 화면에서 조정할 수 없다.
- 안전 상한(5페이지)도 코드 상수 — 화면에서 조정 불가. 더 필요하면 "가져오기"를 다시 누르는 방식으로 우회 가능(사람인에서 수동으로 몇 페이지 넘긴 뒤 다시 클릭).
- 페이지 넘김 중 사람인 쪽 지연(로딩)이 예상보다 길면 다음 파싱이 빈 목록을 받을 수 있다 — 이 경우 "새 후보 0명"으로 감지돼 실제로는 페이지가 더 있는데도 조기 종료할 수 있다. 실사용 검증에서 이 상황이 재현되면 지연 시간을 늘리는 정도로 대응(코드 상수 조정, 별도 설계 불필요).
