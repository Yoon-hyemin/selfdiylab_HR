# 인재검색 자동화 — 실제 후보 리스트에 직무 60점 자동채점 적용 설계

- 원본 명세: `인재검색_자동화_마스터프롬프트_원본.md` 6장(공통 40점)·7장(직무 60점)
- 관련 기존 문서: `docs/superpowers/specs/2026-08-27-talent-search-real-list-import-design.md`(실제 후보 리스트 가져오기 원설계, "채점은 이번 범위가 아니다"라고 명시했던 그 결정을 이번에 부분적으로 뒤집음), `docs/superpowers/specs/2026-08-28-talent-search-list-import-level1-filter-design.md`(방금 끝난 저장 시점 1차 필터)

## 배경

바로 앞 슬라이스(Level1 저장 시점 필터)를 끝낸 뒤, 사용자(윤혜민)가 다음 방향을 요청했다: "1차(Level1 필터, 완료) → 2차(점수 매기기) → 정제된 인원만 검토"하고 싶다. 대화로 다음을 확정했다.

- **2차 판단은 점수 매기기다** — 가상 후보에 이미 쓰고 있는 채점엔진(공통 적합도 40점 + 직무 적합도 60점, `index.html`의 `scoreItemGroup`)을 실제 리스트 후보에도 적용한다.
- **공통 40점은 뺀다.** 공통 40점 항목(목표완결성·오너십, 협업·조율능력 등)은 이력서 본문에서 실제로 확인한 행동 증거가 있어야 판단 가능한데, 리스트 카드에는 그런 근거 자체가 없다(태그·배지는 스킬/구직상태 정보이지 행동 증거가 아니다). 근거 없이 전부 "없음"(50%)으로 고정하면 모든 후보가 똑같은 20/40점을 받아 변별력이 없어서, 아예 계산에서 빼고 **직무 60점만 60점 만점으로 적용**한다.
- **직무 60점의 근거수준은 키워드 매칭도로 추정한다.** 후보의 태그·경력요약·최근경력 메모를 합친 텍스트에서 검색 프로젝트에 등록된 키워드(포함/OR/정확일치/우대)가 몇 개나 발견되는지를 세고, 그 비율로 근거수준(명확/부분/약함/없음) 하나를 정해서 직무 60점 전 항목에 동일하게 적용한다. 항목별로 서로 다른 근거를 지어낼 근거가 없으므로("도구·자격·포트폴리오"는 태그로 어느 정도 판단 가능해도 "직급·독립 수행 범위" 같은 항목은 리스트만으론 전혀 알 수 없다), "이 사람이 이 직무가 찾는 키워드와 얼마나 겹치는가"라는 단일 신호로 전체를 대표시키는 근사치다. 사용자가 이 트레이드오프를 확인하고 승인함.
- **정제된 인원만 기본 노출.** 직무 60점 기준(`정책의 thresholds.jobFitScoreMin`, 현재 42/60)을 넘는 후보만 표에 기본으로 보이고, 미달 인원은 "OO명 더보기"로 접어둔다.

## 이번 슬라이스 범위

**포함**:
- "검색 진행" 화면의 "실제 후보 리스트" 표에 직무 60점·판정(추천/확인 필요) 칼럼 추가.
- 점수 기준(`jobFitScoreMin`) 통과자만 기본 노출, 미달자는 접어서 "더보기"로 확인.
- 점수순 정렬을 기본 정렬로 추가(기존 가져온날짜/나이/태그수 정렬은 그대로 유지, 선택지에 추가).
- 채점 기준을 못 불러온 경우(정책 로딩 실패)의 폴백: 점수 없이 기존처럼 전체 표시.

**제외 (다음 단계로 미룸, 필요시 재논의)**:
- 공통 40점 적용(위 배경 절 참고 — 이 데이터로는 근거 자체가 성립하지 않음).
- `keywords.exclude`(제외 키워드) 매칭 — 이번엔 포함/OR/정확일치/우대만 "긍정 신호 풀"로 쓰고, 제외 키워드 매칭 여부는 건드리지 않는다(범위 확장이라 별도 논의 필요).
- 점수를 사람이 수동으로 조정/override하는 기능(가상 후보의 `manual_status` 같은 것) — 이번엔 계산된 값을 그대로 보여주기만 한다.
- 점수를 DB에 저장하는 것 — 기존 원칙("서버는 원본만, 계산은 클라이언트가 매번") 그대로, 정책이 바뀌면 점수도 다시 계산되어 바뀐다.

## 근거수준 추정 로직

### 입력

- **후보 텍스트 풀**: `tags` 배열 + `careerSummary` + `recentPositions[].note`를 공백으로 이어붙인 뒤 소문자로 변환한 문자열.
- **키워드 풀**: 프로젝트의 `keywords.include` + `keywords.or` + `keywords.exact` + `keywords.preferred`를 합쳐 소문자·중복 제거한 배열(빈 문자열 제외).

### 계산

```
matchedCount = 키워드 풀 중 후보 텍스트 풀에 부분 문자열로 포함된 키워드 개수
totalCount   = 키워드 풀의 개수 (0이면 matchedCount도 0, ratio는 0으로 취급)
ratio        = totalCount === 0 ? 0 : matchedCount / totalCount

근거수준 = ratio === 0        ? '없음'
         : ratio < 1/3        ? '약함'
         : ratio < 2/3        ? '부분'
         : '명확'
```

이 비율 경계값(1/3, 2/3)은 정책 편집 대상이 아니라 코드 상수다 — 정책의 "근거계수"(없음/약함/부분/명확이 각각 몇 %를 받는지)와는 다른 층위의 값이고, 이 프로젝트가 이미 `CAREER_YEARS_GRACE` 같은 값을 상수로 두는 것과 같은 이유다.

### 채점 반영

이 근거수준 하나를 **길이 1짜리 패턴 배열**(`[level]`)로 만들어 기존 `scoreItemGroup(policy.jobFitDefaultWeights, [level], policy.evidenceCoefficients, policy.roundingRule)`에 그대로 넘긴다 — `scoreItemGroup`은 항목 인덱스를 패턴 길이로 나눈 나머지로 근거수준을 찾으므로(`pattern[i % pattern.length]`), 패턴이 1개짜리면 모든 항목이 자동으로 같은 근거수준을 쓰게 된다. 기존 함수를 한 글자도 안 고치고 재사용 가능하다는 뜻이다.

### 판정

```
jobFitScore = scoreItemGroup(...).total   (0~60)
판정 = jobFitScore >= policy.thresholds.jobFitScoreMin ? '추천' : '확인 필요'
```

가상 후보 판정에 있던 "총점(100점) 기준"·"의미 있는 근거 개수 2개 이상" 체크는 이번엔 적용하지 않는다 — 총점 100점은 공통 40점이 없어서 개념 자체가 성립하지 않고, "의미 있는 근거 개수"도 근거수준이 항목마다 다 똑같아서(전부 부분/명확이거나 전부 약함/없음) 사실상 0개 아니면 전체 항목 개수가 되는 퇴화된 지표라 의미가 없다. **`제외` 판정도 없다** — Level1 필터가 이미 저장 시점에 명확한 부적합자를 걸러냈으므로, 저장된 사람은 추천/확인 필요 둘 중 하나로만 나뉜다.

## 화면

- "실제 후보 리스트" 표에 칼럼 추가: **직무60점**, **판정**(배지, 추천=초록/확인필요=회색 — 기존 `verdictBadgeClass` 스타일 재사용).
- 정렬 드롭다운에 "직무 60점" 옵션 추가, **채점 가능한 경우 기본 정렬을 이 옵션으로 바꾼다**(기존 "가져온 날짜" 대신).
- **기본 노출은 판정==='추천'인 행만.** 표 아래에 "확인 필요 N명 더보기" 링크/버튼을 두고, 누르면 나머지를 점수순으로 이어서 보여준다(다시 누르면 접기 — 토글). 미달자가 0명이면 이 링크 자체를 안 보여준다.
- **정책을 못 불러온 경우**(승인 전 프로젝트이거나 버전 조회 실패): 이번 칼럼·필터를 전부 생략하고 기존처럼 원본 정보만 있는 표를 그대로 보여준다(점수 없이) — 검색 진행 화면 자체가 승인된 프로젝트에서만 열리므로 실제로는 거의 발생하지 않는 경로지만, 방어적으로 다룬다.

## 구현 위치

- **정책 로딩 조건 버그 수정 선행 필요**: `index.html`의 `openTalentSearchCandidates()`가 지금은 `if(candidates.length)`(가상 후보가 1개 이상 있을 때만) 정책을 불러온다 — 가상 후보를 한 번도 안 만든 프로젝트에서는 정책 자체가 안 불러와져서 이번 기능(실제 후보 리스트 채점)이 항상 실패한다. `candidates.length` 조건을 없애고 `project.policyVersionId`가 있으면 항상 정책을 불러오도록 고친다(가상 후보 채점 로직에는 영향 없음 — 그쪽은 원래도 정책이 있어야만 동작).
- `index.html`에 새 순수 함수 `scoreListCandidateJobFit(candidate, projectKeywords, policy)` 추가(파일 위치는 `scoreItemGroup` 근처) — 위 로직 그대로 구현, 반환값 `{ evidenceLevel, matchedCount, totalCount, jobFitScore, verdict }`.
- `openTalentSearchCandidates()`가 이미 들고 있는 `policy`/`project`를 `loadTalentSearchListCandidates(projectId, project, policy)`로 전달하도록 시그니처 확장, 모듈 전역 `tsListScoringContext = {project, policy}`에 저장.
- `tsListCandidateRowHtml`이 `tsListScoringContext`를 참고해서 점수·판정 칼럼을 추가로 그린다(정책 없으면 그 두 칼럼 자체를 안 그림 — 표 구조가 조건부로 6칼럼/8칼럼을 오간다).
- `renderTsListCandidatesTable()`에 정렬 옵션 `'jobFitScore'` 추가, 정책 있을 때 기본값을 이걸로, 그리고 추천/확인필요 분리+더보기 토글 상태(`tsListShowBelowThreshold`, boolean) 추가.

## 테스트

- `scoreListCandidateJobFit`은 DOM/네트워크 의존 없는 순수 함수라, `index.html`에서 분리하지 않고 그대로 두더라도(이 프로젝트 관례상 `index.html` 안 로직은 브라우저에서 수동 검증) 개발자 콘솔에서 직접 호출해 경계값(매칭 0개/전체/절반)을 확인한다.
- `development` 브랜치의 실제 승인된 프로젝트로: 키워드와 잘 맞는 후보/전혀 안 맞는 후보를 섞어서 리스트 가져오기 → 표에 정확한 점수·판정이 뜨는지, 기준 미달자가 접혀 있다가 "더보기"로 펼쳐지는지 확인.
- 가상 후보 채점 화면(기존 기능)이 이번 변경으로 안 깨졌는지 회귀 확인 — 특히 `openTalentSearchCandidates()`의 정책 로딩 조건 변경이 가상 후보 없는 프로젝트에서도 정책을 불러오게 되므로, 정책이 있을 때/없을 때 가상 후보 화면 분기가 여전히 올바르게 동작하는지 확인.

## 알려진 한계 (의도적으로 이번 범위 밖)

- 공통 40점 없음(위 배경 절 참고) — 리스트 후보의 "총점"은 100점이 아니라 60점 만점이라는 걸 화면에서 오해 없게 표시해야 한다(칼럼명을 "총점"이 아니라 "직무60점"으로 명확히 함).
- `keywords.exclude` 미반영.
- 근거수준이 항목별이 아니라 전체 단일값이라, 실제 근거 기반 채점보다 정밀도가 크게 낮다 — 어디까지나 "1차로 좁혀진 사람들을 대충 순위 매겨서 검토 순서를 정하는" 용도지, 실제 서류전형 결정 근거로 쓰기엔 부족하다는 걸 화면 설명 문구에 명시한다.
- 점수 수동 조정 불가.
