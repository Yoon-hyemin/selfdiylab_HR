# 인재검색 자동화 — 사람인 검색 실행 자동화 설계

- 작성일: 2026-08-28
- 원본 명세: `인재검색_자동화_마스터프롬프트_원본.md` 3장("사이트별 허용범위가 확인된 경우에만 검색필터 적용과 페이지 이동을 단계적으로 자동화한다"), 8.1.1장("사람처럼 검색하는 검색전략")
- 관련 기존 문서: `docs/superpowers/specs/2026-08-27-talent-search-real-list-import-design.md`, `docs/superpowers/specs/2026-08-28-talent-search-list-import-level1-filter-design.md`(자동 페이지 넘김의 안전장치 원형)

## 배경

Level1 자동필터+자동 페이지 넘김을 끝낸 뒤, 사용자(윤혜민)가 지금까지 만든 것과 원래 원했던 것 사이의 간극을 짚었다: "사람인/잡코리아/리멤버/원티드에서 검색을 누르면 자동으로 우리 조건에 맞게 취합"하고 싶었는데, 지금은 **검색 실행 자체(검색어 입력+검색 버튼)를 여전히 사람이 하고 있고, HR 사이트에 등록해 둔 검색조건(키워드)이 실제 사람인 검색에 반영되지 않는다.**

원본 명세를 다시 확인한 결과, 애초 설계 의도는 "사람이 계속 눌러야 한다"가 아니라 **"사람처럼 보이는 속도로 자동 실행하되, 검증 안 된 위험한 회피 기술(대량 병렬, 스텔스 우회, 지문 조작)은 쓰지 않는다"**였다(3장, 8.1.1장). 이번 세션에서 자동 페이지 넘김에 도입한 "무작위 지연 + 인증화면 감지 시 중단" 안전장치가 정확히 이 원칙을 구현한 것이었는데, 그 적용 범위를 "페이지 넘기기"에만 한정했던 게 좁은 해석이었다. 이번 슬라이스는 같은 안전장치를 "검색 실행"에도 적용한다.

**이번엔 사람인 한 플랫폼만** 다룬다(잡코리아/원티드/리멤버 확장은 여전히 범위 밖 — 플랫폼별 화면 구조가 다 달라서 각각 별도 조사·구현이 필요하다).

## 이번 슬라이스 범위

**포함**:
- 크롬 확장 팝업의 "목표 인원 채우기" 버튼이, 페이지 넘기기 루프를 시작하기 **전에** 먼저 사람인 검색창(OR/AND/NOT 3칸)에 그 프로젝트의 키워드 조건을 채워 넣고 검색 버튼을 누른다.
- 필수조건(`keywords.include`)과 정확일치 문구(`keywords.exact`)는 AND칸에, 핵심조건(`keywords.or`)은 OR칸에, 제외조건(`keywords.exclude`)은 NOT칸에 넣는다.
- 우대조건(`keywords.preferred`)은 검색어로 쓰지 않는다 — 지금도 채점(직무60점 근거수준 추정)에서만 신호로 쓰고 있고, 사람인 검색창에는 애초에 "우대"에 대응하는 칸이 없다.
- 검색 실행에도 페이지 넘기기와 같은 안전장치(무작위 지연, 인증화면 감지 시 즉시 중단)를 적용한다.

**제외 (다음 단계로 미룸)**:
- 사람인 외 플랫폼(잡코리아/원티드/리멤버).
- 검색어 자동 생성·동의어 확장(원본 명세의 로컬 모델 역할, Phase 2) — 지금 있는 키워드를 그대로 사람인 문법에 맞게 옮겨 넣기만 한다.
- 사람인 사이드바의 다른 필터(경력범위, 지역, 스페셜 태그 등) 자동 설정 — 이 시스템의 프로젝트 조건에 대응하는 필드가 없어서 손대지 않는다(아래 "알려진 한계" 참고).

## 사람인 검색창 구조

2026-08-28 실사용 확인: 검색 상단에 3칸짜리 텍스트 입력이 있다(비로그인 튜토리얼 화면에서도 동일한 3칸 UI가 보였다 — `OR 하나 이상의 키워드 포함` / `AND 키워드를 모두 포함` / `NOT 제외할 키워드`, 오른쪽에 "검색" 버튼). **정확한 DOM 선택자는 이번 조사에서 확인하지 못했다** — 로그인 없이 접근한 튜토리얼 페이지에서 iframe 3개가 감지됐고 최상위 문서의 `querySelectorAll('input')`으로는 이 3칸이 잡히지 않았다(실제 로그인된 검색 화면에서는 iframe 없이 최상위 문서에 바로 있을 가능성이 높지만 미확인). **이 프로젝트가 지금까지 반복해온 패턴(카드 선택자, 페이지네이션 버튼 선택자 모두 처음엔 추정치로 구현하고 실제 로그인 화면에서 확인 후 교체)을 그대로 따른다** — 구현 시점에 실제 로그인 세션으로 라이브 DOM을 확인해서 정확한 선택자를 확정한다.

## 값 채우기 방식 — 기술적 위험

사람인 검색 화면은 React 등 프레임워크로 만들어졌을 가능성이 높다(2026-08-27 확인된 `.PageBox`/`.BtnNext` 같은 클래스명 패턴, AJAX 기반 페이지 갱신). 이런 화면의 입력창은 `input.value = '텍스트'`로 값을 바꿔도 프레임워크의 내부 상태(검색 버튼을 눌렀을 때 실제로 서버에 보내는 값)가 갱신되지 않는 경우가 흔하다 — 반드시 네이티브 value setter를 통해 값을 설정한 뒤 `input`/`change` 이벤트를 직접 발생시켜야 한다. 구현 시 이 패턴을 쓴다:

```js
const setter = Object.getOwnPropertyDescriptor(window.HTMLInputElement.prototype, 'value').set;
setter.call(inputEl, text);
inputEl.dispatchEvent(new Event('input', { bubbles: true }));
```

이 기법 자체는 실제 로그인 화면에서 검증해야 한다 — 안 먹히면(값은 화면에 보이는데 검색 버튼을 눌러도 반영이 안 되면) 대체 방법(키보드 이벤트 시뮬레이션 등)을 구현 단계에서 다시 조사한다.

## 흐름

1. 사용자가 "목표 인원 채우기" 클릭.
2. 팝업이 선택된 프로젝트의 `keywords`를 가져와 AND/OR/NOT 문자열을 만든다.
3. 콘텐츠 스크립트에 새 메시지 `FILL_AND_SEARCH`(payload: `{andTerms, orTerms, notTerms}`, 각각 이미 합쳐진 문자열)를 보낸다. 콘텐츠 스크립트가:
   - `isBlockedPage`로 인증화면 여부 확인(감지되면 즉시 `{ok:false, blocked:true}` 응답).
   - 3칸을 찾아 값을 채운다(위 방식). 셋 다 비어있으면(프로젝트에 키워드가 하나도 없는 경우) 채우기·검색 버튼 클릭을 건너뛰고 `{ok:true, skipped:true}`로 응답 — 이미 화면에 있는 검색 결과를 그대로 쓴다(원본 명세의 "확실하지 않으면 건드리지 않는다" 원칙과 같은 결).
   - 검색 버튼을 클릭한다.
   - `{ok:true, skipped:false}` 응답.
4. 팝업은 응답을 받은 뒤 기존 페이지 넘기기와 같은 무작위 지연(`randomPageDelayMs()`, 2.5~4.5초 — 새로 만들지 않고 재사용)을 기다린 다음, 기존 페이지 넘기기 루프(`PARSE_CURRENT_LIST` 반복)로 그대로 이어진다.
5. `FILL_AND_SEARCH`가 `blocked:true`를 반환하면, 페이지 넘기기 루프의 기존 "로그인/인증이 필요합니다" 처리와 동일하게 즉시 중단한다.

## 서버 쪽 변경

확장이 프로젝트 목록을 가져올 때(`GET /talent-search-projects`, 연결 코드 인증) 지금은 `title`/`id`/`status` 등 요약 필드만 내려주고 `keywords`가 빠져 있다. `handlers/talent-search-projects/index.js`의 `project_summary_out`에 `keywords: row.keywords`를 추가한다 — 이미 존재하는 컬럼을 응답에 노출하기만 하는 것이라 마이그레이션은 필요 없다. 이 필드가 늘어나도 HR 사이트 쪽(쿠키세션으로 이 응답을 쓰는 대시보드 카드 목록)은 이 필드를 안 쓰므로 영향 없다.

## 크롬 확장 변경

- `popup.js`: 프로젝트 드롭다운을 채울 때 지금은 `id`/`title`만 쓰고 버리는데, 이제 `approvedProjects` 배열 전체를 모듈 변수로 캐싱해서 버튼 클릭 시 선택된 프로젝트의 `keywords`를 찾을 수 있게 한다.
- `popup.js`: 기존 `buildTalentSearchQueryString`(index.html에 있는, 하나로 합친 문자열 생성 함수)과는 별개로, 이번엔 3칸에 맞춰 따로 만드는 새 헬퍼가 필요하다 — `andTerms = [...keywords.include, ...keywords.exact.map(k => '"'+k+'"')].join(' ')`, `orTerms = keywords.or.join(' ')`, `notTerms = keywords.exclude.join(' ')`. exact 항목에 따옴표를 붙이는 게 실제로 정확일치로 동작하는지는 라이브 검증 대상이다(안 되더라도 AND 조건으로는 동작하니 크게 어긋나지 않는다).
- `list-content.js`: 새 메시지 타입 `FILL_AND_SEARCH` 핸들러 추가.
- `list-content-lib.js`: 입력창 채우기(네이티브 setter+이벤트)와 검색 버튼 탐색을 순수 함수로 분리해서 jsdom으로 테스트 가능하게 한다(단, 실제 선택자는 라이브 확인 전까지 추정치).

## 안전장치 (기존 원칙 재사용, 새로 만들지 않음)

- 인증화면 감지 시 즉시 중단 (`isBlockedPage`, 기존 함수 그대로).
- 무작위 지연 (`randomPageDelayMs()`, 기존 함수 그대로) — 검색 버튼 클릭 후에도 페이지 넘김과 동일한 2.5~4.5초 지연을 적용해서 "검색 즉시 결과 파싱"처럼 부자연스러운 속도가 되지 않게 한다.
- 검색은 여전히 사용자가 "목표 인원 채우기"를 눌러야만 실행된다 — 확장이 스스로 판단해서 검색을 실행하는 자동 트리거는 없다.
- 키워드가 하나도 없으면 검색 버튼을 누르지 않고 건너뛴다(위 흐름 3번) — 빈 조건으로 검색을 눌러서 사람인의 전체 결과나 이상한 상태로 화면을 바꿔버리는 걸 방지.

## 테스트

- `list-content-lib.js`의 새 순수 함수(값 채우기 로직, 검색 버튼 탐색)는 jsdom으로 `node --test`.
- 실제 로그인 세션에서: (a) 검색창 3칸의 정확한 선택자 확인, (b) 값 채우기 기법이 실제로 사람인의 내부 상태를 갱신하는지(검색 버튼을 눌렀을 때 실제로 그 조건으로 필터링되는지) 확인, (c) 정확일치 문구에 따옴표를 붙였을 때 실제로 정확일치로 동작하는지 확인(안 되면 설계 문서·구현 코드에서 그 부분만 수정), (d) 키워드가 없는 프로젝트로 테스트해서 검색 버튼을 건너뛰는 게 맞는지 확인.

## 알려진 한계

- 사람인 사이드바의 다른 필터(경력범위, 지역, 재직상태 등)는 이 시스템이 전혀 손대지 않는다 — 사용자가 사람인에서 미리 설정해둔 값이 검색 버튼 클릭으로 초기화되는지 여부는 확인되지 않았다. 초기화된다면 사용자가 매번 그 필터를 다시 설정해야 하는 불편이 생긴다(라이브 검증에서 확인 필요, 초기화되는 게 확인되면 별도 슬라이스에서 그 필터들도 프로젝트 조건에 추가하는 걸 고려).
- 검색어를 사람인 문법에 맞게 다듬는 것(동의어 확장, 직무 표기 변형 등)은 여전히 안 함 — 프로젝트에 등록된 키워드를 그대로 옮기기만 한다.
- 잡코리아/원티드/리멤버는 이번 범위 밖.
