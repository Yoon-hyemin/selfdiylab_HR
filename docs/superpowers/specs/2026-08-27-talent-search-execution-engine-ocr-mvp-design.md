# 인재검색 자동화 — 실행엔진 OCR 추출 MVP 설계

- 작성일: 2026-08-27
- 원본 명세: `인재검색_자동화_마스터프롬프트_원본.md` (채점 로직·안전 원칙·전체 Phase 로드맵의 1차 출처, 이 문서에서 다시 반복하지 않음)
- 관련 기존 문서: `docs/superpowers/specs/2026-08-19-talent-search-automation-design.md`(Phase 0 — 전체 아키텍처 결정, "실행 엔진만 로컬 분리" 원칙의 출처)
- 이 문서는 그 Phase 0 문서가 미뤄뒀던 **"실행 엔진 자체"**를 처음으로 설계한다. Phase 1A~1E(이 세션 이전까지 완료)는 전부 HR 웹사이트 쪽(기준 관리, 검색 프로젝트 관리, 가상 후보 시뮬레이션)이었고 실행 엔진 코드는 지금까지 하나도 없었다.

## 배경 — 이 세션에서 실제로 확인한 것

사용자(윤혜민, HR팀장)의 실제 크롬으로 사람인(saramin.co.kr) 기업회원 계정에 로그인해서 인재풀 화면을 직접 확인했다. 확인된 사실:

1. **검색결과 리스트**(후보 226명 목록)는 일반 DOM 텍스트로 그대로 읽힌다 — 크롤링 쉬움.
2. **개별 후보 상세 이력서 화면**은 사람인이 스크래핑 방지 목적으로 **텍스트가 아니라 이미지로 렌더링**해서 내려준다 — 화면엔 보이지만 일반적인 페이지 읽기(DOM 파싱)로는 못 읽는다. 요약 카드(나이·경력·학력·연봉)뿐 아니라 스크롤해서 나오는 경력기술서·학력상세·경험/활동/교육까지 전부 이 방식이다.
3. **"인쇄" 버튼은 자동화 경로가 아니다** — 크롬 네이티브 인쇄 다이얼로그(웹페이지 바깥의 OS 레벨 UI)를 띄우는데, 원격 자동화 도구가 이걸 볼 수도 조작할 수도 없고, 설사 사람이 매번 수동으로 눌러도 후보 1명당 사람 손이 필요해서 애초 목표("하나씩 안 열어보고 자동으로 처리")에 안 맞는다. 인쇄/저장 시 사람인이 법적 고지도 띄운다: 저장·출력한 개인정보는 목적 달성 후 5일 이내 파기 책임이 본인에게 있음.
4. **인재풀 진입 시 2단계 인증**이 뜬다(휴대폰 또는 이메일 인증, 6개월간 유효). 원본 명세의 "CAPTCHA·2차인증 발생 시 우회 없이 일시정지, 사용자에게 인계" 원칙 그대로 사용자가 직접 통과시켰다.
5. **사용자의 강한 제약 조건**: 무조건 무료로 할 것 — Claude 등 AI API/토큰을 쓰는 유료 방식을 명시적으로 거부함. 그래서 화면 캡처 → 로컬 OCR(무료 오픈소스)로 텍스트를 복원하는 방식을 검증했다.
6. **Tesseract(무료 오픈소스 OCR) 정확도를 실제 이력서 화면으로 스팟체크**했다 — 결과: 성별/나이/지역/경력기간/학력/직전연봉 같은 핵심 필드와 경력기술서 문단은 대체로 정확했고(글자 사이 이상한 띄어쓰기 정도가 흠), 포트폴리오 URL처럼 복잡한 문자열은 깨졌다. **결론: 핵심 판단 근거를 추출하기에 충분한 수준.**

이 결과로 "무료 로컬 OCR 파이프라인"이 기술적으로 성립한다는 게 확인됐고, 이 문서는 그 파이프라인의 가장 작은 실행 가능 단위(MVP)를 설계한다.

## 이번 슬라이스 범위 (구획화)

**포함**: 사람인 후보 상세 이력서 페이지 하나를 열어놓은 상태에서, 버튼 클릭 한 번으로 전체 내용(스크롤 전체)을 텍스트로 추출해서 화면에 보여준다.

**제외 (다음 슬라이스로 미룸)**:
- 여러 후보 자동 순회/배치 처리
- HR 웹사이트(Vercel+Neon) API 연동 — 추출 결과를 어디에도 전송하지 않는다
- 1B-4c 채점 엔진 연동(점수 계산, Level1 판정 등)
- 사람인 외 다른 플랫폼(잡코리아/리멤버/원티드)
- 검색결과 리스트 자동 순회, 후보 자동 선별

이유: Phase 0 문서가 이미 "실행 엔진은 검색·평가만 하고, 기준·프로젝트 관리는 HR 웹사이트가 담당"이라고 경계를 그어뒀다. 그 경계 안에서도 가장 위험한 미검증 전제(무료 OCR이 실제로 쓸만한가)만 먼저 검증하고, 그 다음 단계(웹사이트 연동, 배치 처리 등)는 이 슬라이스가 실제로 동작하는 걸 확인한 뒤에 따로 설계한다.

## Phase 0 대비 아키텍처 변경사항

Phase 0 문서는 실행 엔진을 "Node.js 백그라운드 프로그램 + 크롬 확장" 조합으로 그렸다. 이번 슬라이스에서는 **Node.js 백그라운드 프로그램 없이 크롬 확장 하나로 끝낸다** — OCR을 서버가 아니라 브라우저 안에서 도는 Tesseract.js(WebAssembly 포팅판)로 처리하기 때문이다. 이렇게 바꾼 이유는 순전히 "무료 + 설치 쉬움"이라는 사용자 제약 때문이다: 별도 프로그램을 설치해서 계속 켜두고 크롬 확장과 통신(네이티브 메시징) 설정을 해야 하는 방식은 비개발자인 사용자에게 설치 단계가 하나 더 늘어난다. 크롬 확장만 추가하면 끝나는 쪽이 지금 시점엔 더 낫다고 판단했다. 이후 슬라이스에서 속도·정확도가 부족하면 그때 네이티브 Tesseract + 로컬 프로그램 조합으로 바꾸는 걸 재검토한다(Phase 0 문서의 원래 방향).

## 구조

```
[크롬 확장 (Manifest V3), 사람인 탭 안에서만 동작]

  콘텐츠 스크립트                팝업 UI
  (이력서 페이지에 주입)          [정보 추출] 버튼
       │                          │ 결과 텍스트 표시(복사 가능)
       │ "스크롤+캡처 시작" 메시지  │
       ▼                          │
  오프스크린 문서 ──OCR 요청──▶ Tesseract.js (kor.traineddata)
       │                          ▲
       └── 캡처된 화면 이미지 ─────┘
```

- **콘텐츠 스크립트**: 이력서 뷰어 영역(DOM 컨테이너)을 찾아 위→아래로 자동 스크롤. 스크롤이 페이지 끝에 닿으면 종료 신호를 보냄.
- **오프스크린 문서**(Manifest V3 백그라운드 서비스워커는 무거운 연산에 안 맞아서, 화면 밖 전용 문서에서 OCR을 돌림): 스크롤 지점마다 `chrome.tabs.captureVisibleTab`으로 화면을 캡처하고, Tesseract.js에 순서대로 넘겨 텍스트로 변환.
- **팝업 UI**: "이 후보 정보 추출" 버튼 하나. 진행 중엔 진행 표시(예: "3/7 구간 처리 중"), 끝나면 전체 텍스트를 한 화면에 모아서 보여주고 복사 버튼 제공.
- 서버·로컬 프로그램·네이티브 메시징 없음 — 크롬 확장 파일 하나가 전부.

## 동작 흐름

1. 사용자가 평소처럼 사람인에 로그인해서 후보 상세 이력서 페이지를 열어둔 상태(이 확장은 로그인을 대신하지 않는다 — 이미 사람이 연 화면에서만 동작).
2. 확장 아이콘 클릭 → 팝업에서 "이 후보 정보 추출" 클릭.
3. 콘텐츠 스크립트가 이력서 영역을 뷰포트 단위로 스크롤하며 각 지점에서 캡처 요청.
4. 오프스크린 문서가 캡처된 이미지를 순서대로 Tesseract.js에 넣어 텍스트로 변환, 구간별 결과를 이어붙임(겹치는 스크롤 구간의 중복 줄은 간단한 문자열 비교로 제거).
5. 완료되면 팝업에 전체 텍스트 표시. 사용자가 읽어보고 필요하면 복사해서 쓴다. 이번 슬라이스는 저장·전송을 하지 않으므로 팝업을 닫으면 결과는 사라진다(다음 슬라이스에서 웹사이트로 전송하게 되면 영구 저장으로 바뀜).

## 안전장치 (원본 명세 원칙 그대로 적용)

- **로그인/2단계인증/CAPTCHA 감지 시 즉시 중단**: 콘텐츠 스크립트가 페이지 URL 패턴(`certification` 등 인증 경로) 또는 특정 문구를 감지하면 캡처를 시작하지 않고 "로그인/인증이 필요합니다 — 직접 처리 후 다시 시도해주세요" 안내만 띄운다. 우회 시도는 절대 하지 않는다.
- **읽기 전용**: 이 확장은 페이지의 어떤 버튼도 대신 클릭하지 않는다 — 제안 보내기, 연락하기, 메시지 발송 등은 원본 명세가 절대 금지한 영역이고, 이번 슬라이스는 애초에 "읽기"만 하므로 그런 버튼 근처에도 안 간다.
- **비밀번호·세션 저장 안 함**: 확장은 사용자가 이미 로그인해 둔 브라우저 세션을 그대로 이용할 뿐, 어떤 인증 정보도 저장하지 않는다.
- **구조 변경 시 실패 안전(fail-closed)**: 이력서 뷰어 컨테이너를 못 찾으면(사람인이 화면 구조를 바꿨을 가능성) 추측해서 아무 영역이나 캡처하지 않고 "이력서 화면을 찾지 못했습니다"로 명확히 실패 표시한다.

## 테스트

- 실제 사람인 후보 2~3명(길이가 다른 이력서)으로 추출 실행 → 화면에 보이는 내용과 결과 텍스트를 사람이 직접 대조.
- 인증 화면(2단계인증 페이지)에서 의도적으로 실행 → 캡처 시작 안 하고 안내 문구만 뜨는지 확인.
- 이력서가 아주 짧은 경우/아주 긴 경우(스크롤 여러 번 필요) 둘 다 확인.

## 다음 단계 후보 (사용자 확인 필요, 아직 미확정)

이번 슬라이스가 실사용으로 검증되면 다음 중 어디로 갈지 다시 논의한다: (a) 여러 후보 자동 순회, (b) 추출 결과를 HR 웹사이트 API로 전송해 1B-4c 채점 엔진과 연결, (c) 사람인 외 플랫폼 확장. 원본 명세 로드맵은 "사람인부터" 순서를 명시하고 있으므로 (c)보다 (a)·(b)가 먼저일 가능성이 높다.
